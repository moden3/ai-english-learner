# 5. サーバーレスのコスト最適化戦略

個人開発における「運用コストの極小化」を実現するためのアーキテクチャ設計指針。
本プロジェクトは、この指針に基づき **完全月額無料 ($0)** で運用できるよう設計されている。

## インフラ基盤の選定
- **EC2 / コンテナ (ECS/EKS) の不使用**:
  - 常時起動するサーバーは固定費が発生する。
  - 完全にリクエスト駆動のサーバーレス構成（Lambda, API Gateway, DynamoDB）に限定。
  - これらはAWSの無料枠（Free Tier）が毎月リセットされるため、個人利用レベルでは課金が発生しない。

## 外部APIの選定と最適化

本プロジェクトでは、AIモデルとして「Google Gemini API」を採用しているが、無料枠を最大限活用しつつ高い品質を維持するために、機能に応じてモデルとオプションを意図的に切り替える「ハイブリッド方式」を実装している。

### 1. AIモデルの明示的な使い分け（標準モデル vs Liteモデル）
Gemini APIには複数のモデルが存在し、それぞれコスト（無料枠の上限）と性能が異なる。
- **`gemini-1.5-flash` (標準モデル)**:
  - **特徴**: 高性能だが、無料枠の上限が厳しい（1日数十回〜数百回程度）。
  - **用途**: 記事の新規作成など、クリエイティビティや高い推論能力が求められる「重い処理」に限定して使用。
- **`gemini-1.5-flash-lite` (Liteモデル)**:
  - **特徴**: 軽量・高速で、無料枠の上限が非常に高い（1日1500回など）。
  - **用途**: 構文解析やキーワード抽出など、プロンプトの指示に従うだけの「単純なテキスト処理」に使用。

UI上でも「高度なAIモデルを使用する (Google検索有効)」というチェックボックス（デフォルト：オフ）を設け、意図した時だけ高度な機能を使うオプトイン設計を取り入れている。これにより、通常時は自動的にLiteモデルが使われ、高性能モデルの無料枠を無駄遣いすることなくアプリ全体の利用可能回数を大幅に引き上げている。

### 2. Google Search 機能の制御 (グラウンディング)
Gemini APIの強力な機能として、AIが回答を生成する前にGoogle検索を行い、最新の情報を取得する機能（Grounding with Google Search）がある。
- **メリット**: 時事問題や最新のテクノロジーなど、AIの学習データに含まれていない「最新のトピック」を指定されても、最新ニュースに基づいた正確な英語記事を生成できる。
- **コスト面の注意点**: Google Search機能を有効にすると、通常のモデル呼び出しとは異なる特別なレートリミットが適用され、無料枠の上限が極端に少なくなる（例：1日20回程度）という仕様がある。

そのため、本プロジェクトではAPIリクエスト時に以下の緻密な制御を行っている。
- **記事生成時 (Generate)**: トピックに関する最新情報が必要なため、標準モデルを使用しつつ Google Search 機能を **ON** にする。
- **解析時 (Analyze)**: すでに生成された英文を翻訳・解析するだけであり外部情報は一切不要なため、Liteモデルを使用しつつ Google Search 機能を明示的に **OFF** にする。

この「検索の要否」と「モデルの使い分け」を組み合わせた戦略が、個人開発においてAI APIのコストを極小化しつつ、質の高いUXを提供する鍵となっている。

## セキュリティによる予期せぬ課金の防止
- **APIキー認証 (`x-api-key`)**:
  - API Gatewayで簡単なキー認証を導入。キーを知らない第三者からのスパムリクエストをエッジ（入り口）で弾く。
  - 不正なLambda起動やGemini APIの浪費を防止。
- **S3 + CloudFrontのOAC設定**:
  - S3URLへの直接アクセスによる意図しないトラフィック増大（データ転送料課金）を防ぎ、必ずCloudFrontのキャッシュを経由させる。
