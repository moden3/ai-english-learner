# 1. アーキテクチャ・デシジョン・レコード (ADR)

このプロジェクト（AI英語学習アプリ）における、主要な技術選定やアーキテクチャ上の意思決定（Architecture Decision Records）をまとめます。
なぜその技術や構成を選んだのかという「背景（Context）」と、他の代替技術との比較結果、および「結果（Consequences）」を記録します。

---

## ADR 000: クラウドプロバイダー（AWS）の採用

- **Status**: Accepted
- **Context**: フルスタックアプリをホスティングする上で、インフラの構築と運用をどこまで自分で行うか（PaaSかIaaS/クラウドか）を決める必要があった。
- **Decision**: AWSを採用し、Terraformを用いたIaC（Infrastructure as Code）でフルサーバーレス構成を構築する。
- **代替技術との比較**:
  | プラットフォーム | 運用オーバーヘッド | カスタマイズ性 (Rust等の自由度) | インフラ構築の学習効果 | コスト (個人開発規模) |
  | :--- | :--- | :--- | :--- | :--- |
  | **AWS (採用)** | 中〜高 (Terraformによる構築) | 非常に高い (Lambda等で自由) | 非常に高い (IaC/クラウド知識) | 最安 (無料枠で0円) |
  | **Heroku / Render (不採用)** | 非常に低い (Git Pushでデプロイ) | 低〜中 (対応言語や環境に制限あり) | 低い (PaaSに隠蔽されるため) | 起動時間が長くなると課金発生 |
- **Consequences**:
  - **メリット**: 無料枠の活用によりコストを極小化でき、IaC（Terraform）やAWSの本格的なクラウドアーキテクチャの学習効果が得られた。また、Rustのネイティブバイナリをカスタムランタイムで動かすといった自由な設計が可能になった。
  - **デメリット**: 初期構築（VPC, IAM, API Gatewayなどの設定）のハードルが高く、PaaSと比べるとデプロイまでの道のりが長い。

## ADR 001: フルサーバーレス・アーキテクチャの採用

- **Status**: Accepted
- **Context**: 個人開発のアプリケーションであり、常時起動型のサーバー（EC2やコンテナ）を配置すると、利用者がいない時間帯でも固定費（月額数千円〜）が発生してしまう。
- **Decision**: AWS Lambda, API Gateway, DynamoDB, S3, CloudFrontを組み合わせた「フルサーバーレス構成」を採用する。
- **代替技術との比較**:
  | 構成 | 固定費 | スケーラビリティ | 運用オーバーヘッド |
  | :--- | :--- | :--- | :--- |
  | **フルサーバーレス (採用)** | なし (0円〜) | 自動（リクエスト単位） | 低（OSパッチ等不要） |
  | **EC2 / VPS (不採用)** | あり (月数千円〜) | 手動（キャパシティ設計） | 高（OS・ミドルウェア管理） |
  | **ECS / EKS (不採用)** | あり (NAT等で高額) | 自動（設定が必要） | 高（コンテナオーケストレーション） |
- **Consequences**:
  - **メリット**: リクエスト時のみコンピューティングリソースを消費するため、AWSの無料枠（Free Tier）内に収まり、**月額0円での運用**が可能になった。
  - **デメリット**: Lambda特有のコールドスタート問題に対処する必要が生じた。

## ADR 002: バックエンド言語としての Rust の採用

- **Status**: Accepted
- **Context**: サーバーレス（Lambda）を採用したため、Node.jsやPythonなどのスクリプト言語では、実行環境の初期化（コールドスタート）に時間がかかり、ユーザー体験（APIのレスポンス速度）が悪化する懸念があった。
- **Decision**: コンパイル言語であり、非常に高速に起動・実行できる **Rust** をバックエンドの言語として採用する。
- **代替技術との比較**:
  | 言語 | 起動速度 (コールドスタート) | メモリ消費 | 学習コスト |
  | :--- | :--- | :--- | :--- |
  | **Rust (採用)** | 非常に高速 (数ms〜) | 非常に低い | 高い |
  | **Node.js (不採用)** | 普通 (数百ms〜) | 普通 | 低い |
  | **Python (不採用)** | 普通 (数百ms〜) | 普通 | 低い |
- **Consequences**:
  - **メリット**: カスタムランタイム (`provided.al2023`) 上でネイティブバイナリとして動作するため、コールドスタートの遅延が数ミリ秒〜数十ミリ秒単位に抑えられ、SPAとの相性が向上した。
  - **デメリット**: Rust特有の所有権やライフサイクルの学習コストがかかる。また、毎回ビルド（`cargo lambda build`）を行う必要がある。

## ADR 003: データベースに DynamoDB (シングルテーブル設計) を採用

- **Status**: Accepted
- **Context**: トピック情報と単語（Vocab）情報を保存する永続化層が必要。RDS（PostgreSQL/MySQL）は常時起動のコストがかかるため不採用。
- **Decision**: フルマネージドなNoSQLである **Amazon DynamoDB** を採用し、PAY_PER_REQUEST（オンデマンドキャパシティモード）で稼働させる。さらに、複数エンティティを1つのテーブルに格納する「シングルテーブル設計」を採用する。
- **代替技術との比較**:
  | データベース | 課金体系 | スキーマ変更 | リレーショナル（JOIN） |
  | :--- | :--- | :--- | :--- |
  | **DynamoDB (採用)** | 従量課金（リクエスト単位） | 柔軟 | 不可（事前設計が必要） |
  | **RDS (不採用)** | 固定費（インスタンス課金） | 厳格 | 可能 |
- **Consequences**:
  - **メリット**: リクエスト単位の課金となりコストが極小化された。テーブルを分割しないため、将来的なプロビジョニング管理も1つで済む。
  - **デメリット**: RDBのように柔軟なJOINができないため、事前にクエリ（アクセスパターン）を設計してPK/SKを決める必要があった。

## ADR 004: フロントエンド技術スタック (Vite + React + Vanilla CSS) の採用

- **Status**: Accepted
- **Context**: 複雑なフロントエンドを効率よく開発しつつ、基礎的な技術（Reactのフックや標準CSS）の学習も兼ねた技術選定が必要だった。
- **Decision**: ビルドツールにVite、UIライブラリにReact、スタイリングにVanilla CSSを採用する。

### 1. ビルドツール (Vite vs Webpack)
| ツール | 開発サーバーの起動速度 | HMR (ホットリロード) | 設定の複雑さ |
| :--- | :--- | :--- | :--- |
| **Vite (採用)** | 非常に高速 (esbuildベース) | 非常に高速 | 低い (デフォルトでモダンな設定) |
| **Webpack (CRA含む)** | 遅い (全バンドル) | 遅い | 高い |
- **選定理由**: 圧倒的な開発体験（DX）の向上と、ビルド設定の手間の削減のため。

### 2. UIライブラリ (React vs Next.js)
| フレームワーク | ホスティングの容易さ | ルーティング | 状態管理の学習 |
| :--- | :--- | :--- | :--- |
| **React (SPA) (採用)** | 容易 (S3 + CloudFrontのみ) | 自前実装 (`useState`等) | 基礎から学べる |
| **Next.js (App Router)** | 複雑 (Vercel以外はサーバーが必要) | ファイルベース (便利) | - |
- **選定理由**: S3での完全な静的ホスティングを実現するため。また、Reactの基本（標準フックによる状態管理）を学習するため。

### 3. スタイリング (Vanilla CSS vs Tailwind CSS)
| 手法 | CSSレイアウトの学習効果 | 記述量 | 外部依存 |
| :--- | :--- | :--- | :--- |
| **Vanilla CSS (採用)** | 高い (Grid/Flexboxを直書き) | 多い | なし |
| **Tailwind CSS (不採用)** | 低い (ユーティリティクラスに隠蔽) | 少ない | あり |
- **選定理由**: 外部フレームワークに依存せず、CSS変数やGlassmorphismなど、標準CSSを使ったモダンなレイアウト技術を習得するため。

- **Consequences**:
  - **メリット**: 高速な開発環境と、S3ホスティングの容易さを両立できた。標準APIに触れることで学習効果が高まった。
  - **デメリット**: ルーティングや複雑なCSSレイアウトをすべてゼロから実装する手間が生じた。

## ADR 005: Gemini API のハイブリッド利用 (1.5-flash / lite)

- **Status**: Accepted
- **Context**: 高品質な英文生成には高度なAIモデルと最新情報（Google Search）が必要だが、それらを毎回使うとAPIの無料枠（レートリミット）をすぐに使い切ってしまう。
- **Decision**: 処理の内容に応じてモデルを使い分けるハイブリッド方式を採用する。
- **代替技術との比較**:
  | アプローチ | APIコスト（無料枠の消費） | 応答速度 | 品質・最新情報 |
  | :--- | :--- | :--- | :--- |
  | **ハイブリッド方式 (採用)** | 最小限に抑えられる | 最適化（解析は高速） | 必要な箇所のみ高維持 |
  | **全て標準モデル (不採用)** | すぐに上限に到達する | やや遅い | 常に高い |
  | **全てLiteモデル (不採用)** | 全く問題ない | 非常に高速 | 低い（複雑生成に不向き） |
- **Consequences**:
  - **メリット**: APIの無料枠を最大限に延命しつつ、必要な箇所でのみ高い回答品質を確保できるようになった。
  - **デメリット**: バックエンド側でのモデル切り替えや、プロンプトチューニングのロジックがやや複雑化した。

## ADR 006: ランタイムでのAPIキー認証と sessionStorage の利用

- **Status**: Accepted
- **Context**: 個人利用のアプリであり、Cognitoなどの本格的な認証基盤（IdP）を導入するのはインフラ構築のオーバーヘッドが大きい。しかし、誰でもAPIを叩ける状態にするとAI APIの浪費（DDoSやスパム）を招く。
- **Decision**: 簡易的な認証として、API Gatewayに `x-api-key` による認証を設ける。フロントエンドでは、初回アクセス時にユーザー自身にAPIキーを入力させ、それを `sessionStorage` に保持する方式を採用する。
- **代替技術との比較**:
  | 認証方式 | 導入コスト（IaC記述量） | セキュリティリスク | ユーザーごとのデータ分離 |
  | :--- | :--- | :--- | :--- |
  | **sessionStorage + APIキー (採用)** | 非常に低い | 低い（キー直書きを回避） | 不可（単一ユーザー想定） |
  | **Amazon Cognito (不採用)** | 高い | 極めて低い | 可能 |
  | **フロントのコード内に直書き (不採用)** | ゼロ | 非常に高い（漏洩リスク） | - |
- **Consequences**:
  - **メリット**: Cognito等のインフラ管理が不要になり、ソースコード（`.env`）にAPIキーを埋め込むセキュリティリスクも排除できた。
  - **デメリット**: 本格的なマルチユーザー運用（ユーザーごとのデータ分離やパスワードリセットなど）には対応できない。あくまで個人利用に特化した割り切った設計である。
